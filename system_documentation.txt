DOCUMENTACION DEL SISTEMA ETL DSSGE
=================================

1. TECNOLOGIAS Y COMPONENTES PRINCIPALES
----------------------------------------
- Lenguaje principal: Python 3.x.
- Librerias clave: oracledb (conexion Oracle), pandas (transformaciones y CSV en memoria), psycopg2 (carga PostgreSQL), python-dotenv (manejo de credenciales), dateutil.relativedelta y datetime (manejo de rangos de fecha), io.StringIO (buffers en memoria para COPY), ademas de librerias estandar como os.
- Motores de base de datos: Oracle (fuente SGSS) y PostgreSQL (repositorio DSSGE con tablas particionadas).
- Configuracion: variables sensibles externas en archivo .env, conexiones construidas dinamicamente al iniciar cada ETL.
- Entorno de ejecucion: multiples scripts independientes con ejecucion directa (sin orquestador central) y procesos abiertos en VS Code / terminales Python dedicadas.

2. ESTRUCTURA GENERAL DEL PROYECTO
----------------------------------
- Carpeta raiz: Scripts/ con subcarpetas organizadas por dominio (ETL_CE_DSSGE, ETL_CE_DWSGE, ETL_CQX_DSSGE, ETL_EME_DSSGE, ETL_HOS_DSSGE, Varios, etc.).
- ETL_CE_DSSGE contiene la mayor cantidad de procesos. Subcarpetas relevantes:
  * Archivos ETL_DIM_* y ETL_DW_* orientados a dimensiones y hechos respectivamente.
  * ETLS ACTUALIZACION: scripts para cargas mensuales de tablas operacionales (ej. ETL_DW_CTCAM10_M, ETL_DW_NOMED, ETL_DW_PROC, ETL_DW_CTPPE10) que sincronizan datos recientes.
  * ETLS D: variantes enfocadas en datos diarios/operativos (consultas externas, homologaciones, historicos).
  * Tablas/: artefactos de soporte como INDICES y TABLAS SES.
- ETL_CE_DWSGE replica los procesos CE con adaptaciones por motor (divisiones Oracle/Postgres) y otras carpetas replican la estructura para CQX, EME, HOS, etc., asegurando consistencia entre lineas de negocio.
- Muchos scripts siguen una plantilla comun: lectura de .env, conexiones Oracle/PostgreSQL, generacion de rango mensual, query parametrizada por mes, truncado de particion destino, carga via COPY.
- Se observan particiones con nomenclatura dssge.<tabla>_<yyyy>_<mm> o sgss_<tabla>_<yyyy>_<mm>, lo que sugiere un modelo de particionado mensual en PostgreSQL.

3. ANALISIS SITUACIONAL DEL SISTEMA
-----------------------------------
Fortalezas
- Plantilla uniforme para los ETL permite mantenimiento predecible (misma estructura de conexion, manejo de fechas y carga).
- Uso de COPY con buffers en memoria evita escritura a disco y acelera las cargas masivas.
- Separacion de credenciales via .env reduce riesgo de exposicion directa en los scripts.
- Particionado mensual en el destino facilita truncado y recargas controladas por periodo.

Riesgos / Debilidades
- Muchos scripts tienen rangos de fechas hardcodeados (p.ej. marzo 2026), lo que requiere intervencion manual para cada ejecucion y aumenta riesgo de omisiones.
- No se observa control de errores avanzado (reintentos, alertas, logging estructurado); los scripts continúan o abortan segun excepciones impresas en consola.
- No existe orquestacion central ni programacion declarada; depender de multiples terminales abiertas dificulta la monitorizacion y la ejecucion en serie.
- El truncado previo a la carga sin respaldo puede generar perdida de datos si una carga falla despues del truncado.
- Ausencia de pruebas automatizadas e indicadores de calidad de datos dentro de los ETL.

Oportunidades de mejora
- Incorporar parametrizacion dinamica de fechas (usar valores relativos al dia actual o argumentos de linea de comandos) para automatizar ciclos mensuales.
- Centralizar la configuracion comun (funciones de conexion, utilidades de fechas) en modulos compartidos para evitar duplicacion.
- Añadir logging estructurado (JSON o tablas de control) y alertas para monitorear exitos/fallos por periodo.
- Evaluar un orquestador (Airflow, prefect, cron centralizado) que ejecute los ETL en orden y gestione dependencias.
- Implementar validaciones post-carga (conteos de filas, checksums) para asegurar calidad y detectar discrepancias frente a Oracle.

4. RESUMEN
----------
El sistema es un conjunto amplio de ETL Python que replica datos operacionales de Oracle hacia PostgreSQL siguiendo particiones mensuales. La consistencia de las plantillas y el uso de librerias maduras son puntos positivos, pero la dependencia de configuraciones manuales, la falta de control operacional y la ausencia de automatizacion representan riesgos. Documentar y orquestar los procesos, junto con mejoras de logging y parametrizacion, aumentaria la resiliencia y trazabilidad de todo el ecosistema DSSGE.

SECCION TECNICA: ETL_CE_DSSGE/ETLS ACTUALIZACION
================================================

1. ETL_DIM_HOMOLOGACION_ENLACES.py
----------------------------------
- Ubicacion: [ETL_CE_DSSGE/ETLS ACTUALIZACION/ETL_DIM_HOMOLOGACION_ENLACES.py](ETL_CE_DSSGE/ETLS%20ACTUALIZACION/ETL_DIM_HOMOLOGACION_ENLACES.py).
- Flujo:
  1. `load_dotenv()` expone dos juegos de credenciales PostgreSQL (`PG_*3` origen y `PG_*` destino) y se instancian dos `create_engine` apuntando a puertos 5432 y 5433 respectivamente.
  2. Se registra `start_time` para medir la duracion total.
  3. Se ejecuta `SELECT * FROM public.homenlaces_historico_total` sobre el origen y se carga en un DataFrame.
  4. Si el DataFrame esta vacio se notifica; de lo contrario se normalizan las columnas a minusculas y se realiza `to_sql(..., if_exists="replace")` contra `dssge.dw_homologacion_enlaces` en el destino.
  5. El bloque `try/except/finally` captura errores y cierra los `engine` con `dispose()`, imprimiendo la duracion al final.

2. ETL_DW_CONSULTA_EXTERNA_HISTORICO_VF2.py
-------------------------------------------
- Ubicacion: [ETL_CE_DSSGE/ETLS ACTUALIZACION/ETL_DW_CONSULTA_EXTERNA_HISTORICO_VF2.py](ETL_CE_DSSGE/ETLS%20ACTUALIZACION/ETL_DW_CONSULTA_EXTERNA_HISTORICO_VF2.py).
- Flujo mensual:
  1. Se cargan credenciales Oracle/PostgreSQL y se definen `month_range(start_date, end_date)` y el intervalo fijo marzo 2026.
  2. Por cada mes se forman `anio`, `mes` (con `zfill` via `%m`) y `tabla_destino = dssge.dw_consulta_externa_<anio>_<mes>`.
  3. La consulta principal toma `sgss.ctaam10` (atenciones ambulatorias) y la enriquece con `cmame10`, `cmper10`, `ctcam10`, `ctppe10`, `ctref10`, etc. Los filtros `atenambatenfec >= start_mes` y `< end_mes+1` garantizan que el rango incluya el primer dia y excluya el siguiente.
  4. Tras extraer, se normalizan las columnas, se trunca la particion destino y se usa `copy_expert` para cargar el CSV en memoria.
  5. Los errores al truncar o copiar provocan `continue`, evitando afectar otros meses; al final se cierran ambas conexiones.

3. ETL_DW_CTCAM10_M.py
----------------------
- Ubicacion: [ETL_CE_DSSGE/ETLS ACTUALIZACION/ETL_DW_CTCAM10_M.py](ETL_CE_DSSGE/ETLS%20ACTUALIZACION/ETL_DW_CTCAM10_M.py).
- Este ETL replica programaciones (`ctcam10`) hacia particiones `dssge.sgss_ctcam10_m_<anio>_<mes>`:
  1. `month_range` basado en `relativedelta` emite [primer dia, primer dia siguiente) por mes.
  2. La query selecciona campos de cita y sus dimensiones (`cmame10`, `cmper10`, `cbtpc10`) filtrando `citambproconfec` en el rango.
  3. Se trunca la particion mensual antes de ejecutar `copy_expert` con las columnas en minusculas.
  4. El script imprime conteos y continua si la tabla destino no existe o si no hay datos ese mes.

- Carga diagnosticos ambulatorios (`ctdaa10`):

  2. El SELECT une `ctdaa10` con `ctaam10` para obtener periodo (`TO_CHAR(trunc(fecha),'yyyymm')`).
  3. Se trunca la particion `dssge.sgss_ctdaa10_anio_v2_<anio>_<mes>` y luego se copia el CSV hacia la tabla padre `dssge.sgss_ctdaa10_anio_v2`.
  4. Cada iteracion maneja errores de truncado/copia y continua con el siguiente mes.

9. ETL_DW_ODONTO.py
-------------------
- Ubicacion: [ETL_CE_DSSGE/ETLS ACTUALIZACION/ETL_DW_ODONTO.py](ETL_CE_DSSGE/ETLS%20ACTUALIZACION/ETL_DW_ODONTO.py).
- Extrae citas odontologicas (`ctaod10` + `ctcam10`):
  1. Usa la misma `month_range` y construye `start_mes_str`/`end_mes_str`.

11. ETL_DW_ZDESERCION_CTCAM10
-----------------------------
- Ubicacion: [ETL_CE_DSSGE/ETLS ACTUALIZACION/ETL_DW_ZDESERCION_CTCAM10](ETL_CE_DSSGE/ETLS%20ACTUALIZACION/ETL_DW_ZDESERCION_CTCAM10).
- Script destinado a analizar desercion de citas (fuente `ctcam10`):
  1. Define dos funciones `month_range` (una generica y otra con `relativedelta`); la segunda es la utilizada en el bucle.
  2. El rango fijo enero 2026 se procesa mes a mes construyendo la clausula `citambsolfec BETWEEN start_mes AND end_mes` (ambos inclusivos).
  3. Tras extraer los datos enriquecidos con `cmame10`, `cmper10`, `cbtpc10`, se trunca la particion `dssge.sgss_ctcam10_desercion_<anio>_<mes>` y se carga con `copy_expert`.

Notas comunes
-------------
- Todos los ETL mensuales emplean buffers `StringIO` para alimentar `COPY FROM STDIN`, normalizan las columnas a minusculas y ejecutan `TRUNCATE TABLE` previo a la carga.
- Las funciones `month_range` cubren el primer dia del mes (`>=`) y excluyen el primer instante del mes siguiente (`<`), salvo el caso de desercion que utiliza `<= end_mes`.
- Las fechas actuales estan hardcodeadas (marzo 2026 en la mayoria); para automatizar bastaria con reactivar los bloques comentados que usan `datetime.today()` y `relativedelta`.
